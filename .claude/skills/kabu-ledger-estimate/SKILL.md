# kabu-ledger-estimate — 次期売上・利益のフェルミ推定

**目的は的中ではない。** 何が重要な変数なのか・どんな規模感なのかを、
検証可能な形で外部化すること。だから:

- **計算はコード**（`src/estimate.py`）。このスキルがやるのは分解と値の選定だけ
- **仮定は隠さない。** 変数1つごとに `basis`（actual／disclosed／assumed）を必ず付ける
- **モデルは書き換えない。** 数値感が変わったら新しい版を `models:` の末尾に足す
  （変遷そのものが学習の履歴。過去版の削除・修正は禁止）

## 手順

### 1. 材料を読む（この順で・最小限）

- `data/fundamentals/{code}.csv` — status に OK を含む行が実績の正（D53 と同じ規律）
- `data/tanshin/{code}.csv` — 一次情報（あれば）。セグメント情報はここが最良
- `reports/{code}.md` の「この会社は何者か」「財務の推移と健全性」— 事業構造の把握

### 2. フェルミ分解（変数は少なく）

売上を 2〜5 セグメントに分け、各セグメントを **変数2〜4個の掛け算**で表す
（例: `stores * sales_per_store`）。変数が多いほど賢く見えるが、
感度分析で効かない変数はノイズ。**桁が合うことを優先する。**

`basis` の規律:

| basis | 条件 | 必須項目 |
|---|---|---|
| `actual` | fundamentals の status=OK 値から導いた | `source`（CSV パス） |
| `disclosed` | 一次情報（短信・開示PDF）に書いてある | `source`（URL＋取得日） |
| `assumed` | 推定した | `note`（**どう推定したか**。無根拠の数字は書かない） |

### 3. 直近動向で数値感を置き換える

この数カ月のマクロ・業界・個別の動きを調べ、変数の値を見直す。
ニュースは `python src/fetch_news.py --codes {code} --days 90` の見出しから拾い、
必要なら Web 検索で補う（**全て出典URL＋取得日つき**。出典の無い置き換えはしない）。
置き換えた変数は `note` に「何を受けてどう変えたか」を書く。

### 3.5 市場予想（コンセンサス）を記録する

ファイル先頭の `market_forecast:` に、市場予想（アナリストコンセンサス・四季報予想等）
の売上・営業利益を **source（URL＋取得日）つき**で書く。
**カバーが無い銘柄は `note` にその旨を書く**（無いことも情報。黙って省略しない）。
台帳は「会社計画・市場予想・当台帳推定」を並べ、推定の市場予想比±%を機械表示する。

### 4. 計算と感度（コードに任せる）

```powershell
$env:PYTHONIOENCODING = "utf-8"
python src/estimate.py --code {code}
```

検証エラー・推定売上・営業利益・**感度分析**（どの変数が営業利益を最も動かすか）・
会社計画との比較が出る。**暗算で数字を出さない。** 感度上位の変数こそ
`note` と `source` を厚くする（そこが投資判断の急所）。

### 4.5 論理の自己点検（confirmed に上げる前に）

計算の**ロジック**を疑う: 二重計上（セグメント間の重複・内部取引）、年率換算の
季節性、期中平均と期末の混同、利益率の適用範囲（全社×総売上 か セグメント別か）、
単位の混在。おかしければ**新しい版**として直す（過去版は残す）。

### 5. マスターの確認（必ず止まる）

`status: draft` のままモデル全文と感度上位3変数をマスターに提示し、
承認を得てから `status: confirmed` に変えて commit する。
**承認前に confirmed にしない。** draft のまま公開された場合、台帳には
「未確定」の印が出る（隠す方法は無い）。

### 6. 検査と反映

```powershell
python src/checks.py          # estimates の形式検査を含む。FAIL 0 を確認
python src/build.py
git add estimates/ docs/ ; git commit ; git pull --rebase origin main ; git push
```

## やってはいけないこと

- **判定スタンプ（judge.py）への接続。** 推定は読み物であり、ゲートではない
- `predictions/*.yaml` への登録（あちらは人間だけが登録する別の仕組み）
- 指値・売買方針・ポジション意向を書くこと（公開リポジトリ）
- 決算が出たあとに過去版を「当たっていた形」に直すこと（答え合わせは
  `estimate.py` が fundamentals の実績から機械で表示する）

## 更新のタイミング

決算・業績修正・大型開示のとき（深掘りの後続として）、またはマスターの指示。
**週次ルーティンでは回さない**（週次は追記だけの軽い工程を保つ）。
